# 目标模式自决停止与迭代预算对齐方案

> 状态: 已落地 | 最后核对: 2026-09-16

## 背景

目标模式（spark-loop）此前把「迭代轮次」当作主停机条件：`setGoal` 未显式传 `budget` 时默认
`{ maxIterations: 12, maxConsecutiveFailures: 3, noProgressLimit: 3 }`，泵循环在
`progressLog.length >= 12` 时直接判定 `stopped_by_budget`，输出 "Goal stopped after 12 iterations."。

问题有两点：

1. 长任务 12 轮远不够用，且 `GoalRepository` 没有 `updateBudget`，目标一旦起跑轮次上限就冻结，用户只能等停掉后重建目标。
2. 触顶后目标进入终态，不能续跑；用户无法区分「真的做完了」和「被轮次掐断」。

## 竞品对照

| 产品 | 主停机条件 | 轮次上限 | 触顶/中断后 |
| --- | --- | --- | --- |
| Codex CLI | 模型自驱，认为完成即停 | 无轮次配置项；长任务靠上下文压缩支撑 | 唯一预算 `rollout_budget` 按 token 计，默认关闭 |
| Claude Agent SDK | 模型不再调用工具即结束 | `maxTurns` 可选，不设=不限 | 另有 `maxBudgetUsd` 可选 |
| OpenHands `/goal` | 每轮 LLM judge 审计目标完成度 | 默认 10 仅兜底，`/goal --max N` 可自定义 | `capped` ≠ `complete`，`/goal/resume` 可续跑 |
| Devin / Copilot cloud agent | 跑到完成，按用量计费 | 无轮次上限 | 人工随时打断 |

结论：没有主流实现把「固定轮次」当作主停机机制。目标模式的自决性应来自模型对完成度的判断，
轮次只适合做防跑飞的保险丝，且必须可调、触顶不等于完成。

## 落地方案（本次范围）

最小改动、对齐「模型自驱完成」：

1. **默认不设轮次上限**：`setGoal` 不传 `budget` 时只写 `{ maxConsecutiveFailures: 3, noProgressLimit: 3 }`，
   两类卡死熔断保留为兜底。
2. **显式配置仍生效**：调用方传 `budget.maxIterations` 时行为不变，达到上限仍 `stopped_by_budget`。
3. **迭代 prompt 不再捏造上限**：未设置 `maxIterations` 时进度头输出 `Recent progress (iteration N):`，
   不再回落成 `of 12`，避免向模型暗示不存在的轮次预算。
4. **前端零改动**：`GoalIterationDivider` 与 `ChatGitEnv` 早已对 `maxIterations == null` 做分支，
   事件映射层只在字段为数字时透传。

## 第二步：停机可续跑与「预算周期」（本次范围）

去掉轮次上限后，剩下的停车条件（显式 `maxIterations` 与两类卡死熔断）仍是**没有出口的终态**：
`startGoalLoop` 一进循环就重新判定同一份 `progressLog`，暂停/恢复之外没有任何「继续」入口，
渲染端还在 `goal_budget_stopped` 时把 `activeGoal` 置空、目标区块连同按钮一起消失——
用户只能清除目标重建，与「完成用户目标为一切前提」相悖。本次补齐：

1. **预算周期（budget cycle）**：周期起点 = 目标创建时刻，或**停机之后的第一次「继续」**。
   轮次/运行时长/成本/熔断都在当前周期内结算，因此「继续」是一次明确的再运行授权。
   - 暂停 → 恢复**不算**新周期：`maxRuntimeMinutes` 的「排除暂停时长但继续累计」语义不变
     （否则暂停一次就能白拿一份时长额度）。
   - 只有 `goal_budget_stopped` 之后的第一次 `goal_resumed` 才切周期，事件按 goalId 过滤；
     事件读取失败（旧库、测试 double）按「未停机过」处理，周期起点回落 `createdAt` ≈ 旧行为。
2. **轮次口径跟随周期**：迭代 prompt 的进度头改为 `iteration <本周期轮次> of <M>`，
   跨周期时附注 `N iterations overall across budget cycles`，不再出现「第 3 轮 / 共 2 轮」
   这种自相矛盾的预算暗示（那会让模型误判超额而提前收口）。
3. **续跑入口**：`ChatGitEnv` 在 `stopped_by_budget` 状态提供「继续」（走既有 `session:goal-control`
   的 `resume`）；`event-mapper` 不再把停机当终态清空 `activeGoal`，`goal_completed/failed/cleared`
   仍按原语义下线快照。

## 行为矩阵

| budget.maxIterations | 轮次停车 | 迭代 prompt 进度头 | 前端展示 |
| --- | --- | --- | --- |
| 未设置（默认） | 不停，跑到模型自报 completed/blocked/failed | `Recent progress (iteration N):` | `第 N 轮` |
| 显式 N | 周期内条目数 `>= N` 时 `stopped_by_budget` | `Recent progress (iteration N of M):` | `第 N 轮 / 共 M 轮` |

其余熔断不受影响：`maxBudgetUsd`、`maxRuntimeMinutes`、`maxConsecutiveFailures`、`noProgressLimit`。
以上所有预算/熔断的计数都限定在当前预算周期内（见上节）；停机后点「继续」即获得新的周期额度。
