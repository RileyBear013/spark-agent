# Git 提交行右键菜单与提交引用加入会话

> 状态: 已落地 | 最后核对: 2026-09-17

## 背景

代码编辑面板左侧「Git」面板的提交列表里，一条提交的信息在界面上是只读的：
要拿提交 ID 只能悬浮等待详情浮层再点复制按钮；要拿提交信息（标题 + 正文）没有入口；
想让 Agent 看某条提交，只能手动从终端里 `git show <hash>` 再复制粘贴。

目标：提交行右键直接提供「复制提交 ID」「复制提交信息」「添加到会话」三项，
其中「添加到会话」与文件树右键「添加到对话」保持同一套交互——在会话输入框里生成一个
可移除的引用 chip，而不是把内容灌进正文。

## 方案

### 1. 右键菜单（提交列表行 + 提交内文件历史行）

- 新增 `GitCommitContextMenu`（createPortal 到 body + fixed + 视口 clamp，
  点击外部 / Esc / 滚动即关闭），开合状态由 `useGitCommitContextMenu` 持有。
  两者拆成两个文件，避免「同文件混合导出 hook 与组件」的 react-refresh 告警。
- 提交列表行（`GitCommitHistory`）右键时先收起悬浮详情浮层，避免两个浮层挂同一行。
- 提交展开后的「文件历史」行同样是提交，右键复用同一菜单。
- 复制走 `navigator.clipboard`（与提交详情浮层的复制按钮一致），成功/失败都有 toast。
- 复制提交信息 = 标题 + 正文（`formatGitCommitMessageText`，正文缺失时只给标题）。

### 2. 提交引用 chip（输入框内）

- `composerInsert` 追加通道新增第四类载荷 `commitReferences: CommitReference[]`
  （`hash` / `shortHash` / `subject`），与代码位置引用、附件共用同一条
  `spark:code-viewer:insert-to-composer` 通道，调用方无需知道 composer 实例。
- 状态按草稿桶（会话）隔离，与代码位置引用完全同构：`composer-commit-references`
  提供去重合并、桶更新与跨桶清理；草稿桶被回收 / 清空 / 发送后一并清理。
- chip 由 `ComposerCommitReferenceStrip` 渲染：双行（上行短 hash、下行提交标题）+ ✕ 移除，
  样式与代码位置引用 chip 同源，无新增视觉语言。

### 3. 发送时的正文拼接规则

三类引用（代码位置 / 浏览器元素 / Git 提交）统一走 `appendComposerReferenceBlock`：

- 用户没写正文 → 引用文本替换 fallback 占位（如「请查看附件。」），保留回复引用前缀；
- 用户写了正文 → 追加到正文末尾；
- 多类引用同时存在 → 只有第一个替换占位，后续追加。

最后一条修掉了原实现的一个静默丢行问题：旧代码对每类引用都做
`text.replace('请查看附件。', ...)`，占位被前一类替换后，后一类的 `replace` 匹配不到，
引用文本会被丢弃。提交引用加入后该组合（代码位置 + 提交引用）成为高频路径，必须修。

提交引用发送为 `[Git 提交] <短hash> <标题>`（与浏览器元素引用 `[浏览器元素引用]` 前缀同构），
模型可按需 `git show` 回查改动，避免把 diff 灌进正文。

## 兼容性与风险

- 只新增菜单与引用类型，不改动 IPC / 协议 / 持久化结构；提交数据仍走既有 `workspace:git-log`。
- 提交引用是纯渲染层状态，不进草稿持久化，不改变既有草稿格式。
- 原有代码位置引用、浏览器元素引用、附件行为不变（仅多类引用共存时的丢行问题被修正）。
- 引用 chip 与附件共用输入框上限逻辑之外的独立通道，不影响附件 20 条上限。
